# Як ми працюємо з репозиторієм

## Гілки

| Гілка | Хто | Що |
|---|---|---|
| `main` | — | Захищена. Тільки робочий, перевірений код. Прямий push заборонений. |
| `feature/domain` | Напрям 1 | Доменні класи, винятки, CONTRACTS.md |
| `feature/storage` | Напрям 2 | Серіалізація, CLI, тести |
| `feature/analytics` | Напрям 3 | pandas-аналітика, декоратор, дашборд |

Почати роботу:

```bash
git switch main
git pull
git switch -c feature/<напрям>
```

Час від часу підтягувати свіжий `main` у свою гілку, щоб конфлікти не накопичувались:

```bash
git fetch origin
git merge origin/main
```

## Pull request

1. Усе потрапляє в `main` **тільки через PR** зі своєї гілки.
2. PR переглядає хоча б один інший учасник.
3. Перед відкриттям PR:
   - `python -m pytest` проходить (або в описі PR написано, які тести червоні й чому);
   - `python -c "import task_manager.domain"` працює;
   - якщо змінився публічний API — оновлено `docs/CONTRACTS.md`.
4. В описі PR: що зроблено, що змінилось для інших напрямів, як перевірити.

## Формат комітів

```
<тип>: <що зроблено, з малої літери>
```

| Тип | Коли |
|---|---|
| `feat:` | нова функціональність |
| `fix:` | виправлення помилки |
| `test:` | тести |
| `docs:` | документація, README, CONTRACTS |
| `refactor:` | зміна коду без зміни поведінки |

Приклади:

```
feat: Task.change_status з таблицею переходів
fix: completed_at не скидався при скасуванні
test: параметризовані переходи статусів
docs: формат to_dict для TeamMember
```

Комітимо дрібно: один коміт — одна логічна зміна.

## Головне правило

**Змінив публічну сигнатуру — попередь у чаті до того, як запушив.**

Публічна сигнатура — усе, що описано в `docs/CONTRACTS.md`: назви класів, атрибутів,
методів, параметрів, типи, винятки, формат словників. Мовчазна зміна ламає роботу
двох інших людей.

## Синки

Коротко раз на 2–3 дні: хто де застряг, що змінилось у контрактах.
