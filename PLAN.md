# Система управління завданнями команди — план роботи

## Що будуємо в підсумку

Консольний застосунок на чистому Python + окремий дашборд аналітики на Streamlit.

Стан зберігається в **JSON**, бази даних немає — це прямо з умови завдання.
Веб-сайт **не робимо**: він не входить у жоден із трьох напрямів і забере час у всіх.

**Чому чистий Python, а не Django/FastAPI:** Напрям 1 оцінюють за ООП — наслідування, абстрактні класи, поліморфізм. Django-моделі це не звичайні класи (там метакласи й ORM-магія), тому фреймворк сховає рівно те, що треба показати. Плюс ORM конфліктує з вимогою зберігати стан у JSON.

## Структура проєкту

```
task_manager/
  domain/            ← Напрям 1
    enums.py         (Status, Priority)
    notifiable.py    (абстрактний базовий клас)
    task.py
    project.py
    team_member.py

  storage/           ← Напрям 2
    serializer.py    (JSON: save / load)
    exceptions.py

  analytics/         ← Напрям 3
    stats.py         (pandas)
    decorators.py

  cli.py             ← Напрям 2 (точка входу)
  dashboard.py       ← Напрям 3 (Streamlit)

tests/               ← Напрям 2
data/state.json
```

## НАПРЯМ 1 — архітектура та ООП

Пише доменні класи. Це фундамент, від нього залежать двоє інших — тому стартує першим.

### Файли

**`enums.py`**
- `Status`: TODO, IN_PROGRESS, REVIEW, DONE, CANCELLED
- `Priority`: LOW, MEDIUM, HIGH, CRITICAL
- Через `Enum`, не рядки і не константи

**`notifiable.py`**
- Абстрактний клас `Notifiable` з `@abstractmethod get_notification_message()`
- Метод **формує текст повідомлення, а не відправляє його**
- Доставка сповіщень — не справа доменних класів

**`task.py`**
- Атрибути: `title`, `description`, `status`, `priority`, `assignee`, `deadline`, `created_at`
- Методи: `change_status()`, `assign_to()`, `is_overdue()`

**`project.py`**
- Атрибути: `name`, `tasks`, `members`
- Методи: `add_task()`, `add_member()`, `get_tasks_by_status()`, `completion_rate()`

**`team_member.py`**
- Атрибути: `name`, `email`, `role`, `assigned_tasks`

### Ключове

- Усі три сутності успадковують `Notifiable` і **по-своєму** перевизначають повідомлення:
  - `Task` → про зміну статусу
  - `Project` → про наближення дедлайну
  - `TeamMember` → про призначене завдання
- Правила переходів статусів: `TODO → IN_PROGRESS → REVIEW → DONE`. Стрибок `DONE → TODO` заборонений

### Головне обмеження

**Доменні класи не знають ні про JSON, ні про pandas, ні про консоль.**

Жодного `save_to_file()` всередині `Task`. Саме ця розв'язаність дозволяє трьом людям працювати паралельно, а не чекати одне одного.

## НАПРЯМ 2 — інфраструктура та якість

Відповідає за те, щоб система пережила перезапуск, не падала від дурного вводу і мала докази того, що логіка працює.

### Файли

**`exceptions.py`** — власна ієрархія винятків

```
TaskManagerError                    ← базовий, від нього все решта
├── MemberNotFoundError             ← призначення завдання неіснуючому учаснику
├── TaskNotFoundError               ← звернення до завдання, якого немає
├── InvalidStatusTransitionError    ← спроба DONE → TODO
├── DeadlineInPastError             ← дедлайн у минулому
└── StorageError                    ← файл пошкоджений або недоступний
```

Чому власні, а не вбудовані `ValueError` / `KeyError`: спільний базовий клас дозволяє в CLI написати один `except TaskManagerError` і піймати всі наші помилки, не глушачи справжні баги. Кожен виняток має нести контекст — не просто «не знайдено», а ім'я учасника чи ID завдання.

**`serializer.py`** — збереження і завантаження стану

- `to_dict()` / `from_dict()` для кожної сутності
- `save_state(project, path)` / `load_state(path)`

**Три технічні пастки, які тут точно виникнуть:**

1. **`datetime` і `Enum` не серіалізуються в JSON напряму.** Треба `deadline.isoformat()` при записі й `datetime.fromisoformat()` при читанні, `status.value` при записі й `Status(value)` при читанні.

2. **Циклічні посилання.** `Task.assignee` вказує на `TeamMember`, а `TeamMember.assigned_tasks` містить ті самі `Task`. Наївний `to_dict()`, який рекурсивно розгортає обʼєкти, зациклиться й впаде з `RecursionError`.
   **Рішення:** серіалізувати посилання **за ID**, а не вкладеним обʼєктом. У JSON `Task` зберігає `"assignee_id": "..."`, а не весь словник учасника.

3. **Двопрохідне завантаження.** Через попередній пункт `load_state()` не може створити обʼєкти за один прохід: у момент створення `Task` потрібного `TeamMember` ще може не існувати.
   **Рішення:** спочатку створити всі обʼєкти без звʼязків, скласти в словник `{id: obj}`, другим проходом проставити посилання.

Це найважче місце в усьому проєкті. **Обговорити з Напрямом 1 на Етапі 0** — від цього залежить, чи будуть у сутностей ID-поля.

**Бонус, якщо буде час:** атомарний запис — пишемо у тимчасовий файл, потім `os.replace()`. Інакше падіння посеред запису лишає пошкоджений `state.json` і весь стан втрачено.

**`cli.py`** — точка входу застосунку

- Головний цикл меню: створити проєкт, додати учасника, створити завдання, призначити, змінити статус, показати список, зберегти, вийти
- Валідація вводу: користувач вводить букву замість номера, порожній рядок, дату в невірному форматі
- **Обробка винятків на межі:** доменні класи *кидають* винятки, CLI їх *ловить* і показує людське повідомлення. Ніде в CLI не має бути `except: pass`
- Автозбереження при виході, завантаження стану при старті

**`tests/`** — pytest

- `conftest.py` з фікстурами: готовий проєкт із кількома учасниками й завданнями
- Переходи статусів: валідні (`TODO → IN_PROGRESS`) і невалідні (`DONE → TODO` має кидати `InvalidStatusTransitionError`)
- `parametrize` на матриці переходів — усі комбінації статусів одним тестом
- Прострочені дедлайни: `is_overdue()` на завданні з датою в минулому і в майбутньому
- Призначення завдання неіснуючому учаснику → `MemberNotFoundError`
- **Round-trip серіалізації:** обʼєкт → JSON → обʼєкт має дати рівно те саме. Найважливіший тест у цьому напрямі, бо ловить одразу всі три пастки вище
- Завантаження пошкодженого JSON → `StorageError`, а не падіння

**Мінімум:** 15–20 тестів. Не ганятись за 100% покриттям — покривати те, де баг найдорожчий.

### Що потрібно від інших

- Від **Напряму 1**: скелети класів із сигнатурами (Етап 1). Тести можна писати проти скелетів, поки логіки ще немає — вони просто будуть червоні, і це нормально
- Рішення про ID-поля в сутностях — узгодити на старті

## НАПРЯМ 3 — аналітика

Відповідає за те, щоб із набору обʼєктів отримати відповіді на питання «хто перевантажений», «чи встигаємо», «на що йде час».

### Файли

**`decorators.py`** — логування зміни статусу

- Декоратор обгортає метод `Task.change_status()` і пише в лог: що за завдання, зі статусу в статус, коли
- Обовʼязково `functools.wraps` — інакше зникне імʼя функції й докстрінг, і це помітять на захисті
- Використовувати модуль `logging`, не `print`. Налаштувати запис у файл `logs/status_changes.log`
- Декоратор має бути **загальним**, а не тільки під `change_status` — тоді його можна повісити й на інші методи

**Координація:** декоратор пише Напрям 3, а застосовує до методу Напрям 1. Домовитись, хто ставить `@log_status_change` над методом.

Можна писати з першого дня — не залежить від готовності класів.

**`stats.py`** — pandas-аналітика

**Найважливіша частина — міст між обʼєктами і DataFrame.** У вас є список обʼєктів `Task`, а pandas працює з таблицями. Потрібна функція, яка розкладає обʼєкти в плоскі рядки:

```
tasks_to_dataframe(project) → DataFrame з колонками:
    task_id, title, status, priority, assignee_name,
    deadline, created_at, is_overdue
```

Далі все рахується як звичайний pandas. Три метрики з умови:

**1. Завантаженість учасників**
- Кількість завдань на кожного (`groupby('assignee_name').size()`)
- Розподіл за статусами всередині учасника (`pivot_table` або `crosstab`)
- Скільки з них у роботі просто зараз, скільки прострочено

**2. Відсоток виконання завдань у строк**
- Серед завдань зі статусом DONE — у скількох завершення відбулось до дедлайну
- **Увага:** для цього потрібне поле `completed_at`. Якщо його немає в моделі — попроси Напрям 1 додати. Обговорити на Етапі 0, потім буде пізно
- Розбивка по учасниках і по пріоритетах

**3. Розподіл завдань за пріоритетами**
- Скільки завдань кожного пріоритету
- Перетин пріоритету зі статусом: чи не висять критичні завдання в TODO
- Середній час виконання по пріоритетах

**Як працювати до готовності Напряму 1:** напиши генератор фейкових даних — функцію, яка створює 50–100 випадкових завдань зі схожою структурою. Так можна робити всю аналітику паралельно, а на Етапі 3 просто підмінити джерело.

**`dashboard.py`** — Streamlit

- Чистий Python, без HTML і JS
- `st.title()`, `st.metric()` для ключових цифр, `st.dataframe()` для таблиць, `st.bar_chart()` для графіків
- Мінімум три секції під три метрики вище
- Фільтри через `st.selectbox()` — вибір учасника, статусу, пріоритету
- Запуск: `streamlit run dashboard.py`

Приблизно півдня роботи, вигляд солідний.

**Якщо Streamlit не заходить:** matplotlib-графіки, збережені в PNG, теж закривають вимогу — просто менш ефектно.

### Що потрібно від інших

- Від **Напряму 1**: перелік полів у сутностях і рішення про `completed_at`
- Від **Напряму 1**: місце, куди повісити декоратор
- Від **Напряму 2**: нічого критичного — можна читати стан напряму з обʼєктів, не через JSON

## Що фіксуємо на старті

**Напрям 1 віддає першим**, решта без цього не почне:

1. Повний перелік класів і їхніх публічних атрибутів
2. Сигнатури методів, які викликатимуть інші напрями
3. Формат словника для `to_dict()` — без цього Напрям 2 заблокований
4. Які поля потрібні аналітиці

**Три рішення, які треба ухвалити всім разом на Етапі 0** — потім переробляти дорого:

- **Чи є в сутностей ID?** Від цього залежить, як Напрям 2 розвʼязуватиме циклічні посилання при серіалізації. Без ID доведеться викручуватись
- **Чи є в `Task` поле `completed_at`?** Без нього Напрям 3 не порахує відсоток виконання в строк — а це прямо в умові завдання
- **Хто ставить декоратор** `@log_status_change` над методом `change_status()` — Напрям 1 при написанні чи Напрям 3 при інтеграції

## Як працюємо

- **Гілки:** `main` + окрема гілка на людину. У `main` тільки через pull request
- **Головне правило:** змінив публічну сигнатуру — пишеш у чат **до того**, як запушив. Мовчазна зміна ламає роботу двох інших людей
- **Синки:** коротко раз на 2–3 дні, хто де застряг
- **Пусті класи-заглушки краще за відсутність класів.** Віддати скелет на день раніше цінніше, ніж ідеальну реалізацію на три дні пізніше
